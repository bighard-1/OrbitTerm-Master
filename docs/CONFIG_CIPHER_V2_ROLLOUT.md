# 配置密文 V2 灰度发布

V2 迁移保持零知识边界：客户端本地解密 V1、生成 V2 密文并验证；后端只在同一 PostgreSQL 事务中比较旧密文摘要和向量时钟，再写入完整账户快照。后端不会接收主密码或明文。

## 发布前条件

1. `Backend PostgreSQL Gate` 为绿色，且当前提交对应的 CI 证据可见。
2. 使用不可变 Git SHA 构建镜像，并记录 GHCR digest；不要用 `latest` 作为灰度或回滚依据。
3. 为目标环境完成 PostgreSQL 可恢复备份，并记录备份校验值。
4. 目标环境使用与生产隔离的数据库、JWT 密钥和测试账户。
5. 参与迁移的 Apple/Android 客户端均已具备 V2 reader；旧客户端仍可读取 V1，不应被用作迁移验证者。

## 预发布步骤

1. 以固定镜像 digest 部署候选版本，保持 `CONFIG_CIPHER_V2_MIGRATION_ENABLED=false`。
2. 验证 `/healthz` 为 200，且未授权请求迁移地址返回 404。
3. 在预发布将该变量设为 `true` 并仅重建 API 容器；确认未授权请求变为 401，证明端点存在且仍受 JWT 保护。
4. 使用独立测试账户创建至少一条 V1 密文资产和一条回收站密文资产；用 V2 客户端执行迁移。
5. 验证每条云端密文均为 V2、迁移后可由另一端读取；再制造向量时钟/密文摘要冲突，确认请求得到 409 且没有任何记录被部分更新。
6. 保持开关关闭，使用旧镜像验证正常的既有同步仍可工作；已经迁移成 V2 的数据只能由具备 V2 reader 的客户端读取。

## 生产灰度与回滚

1. 在变更窗口前再次备份并记录旧镜像 digest。
2. 先部署固定候选镜像，但保持开关为 `false`；验证健康检查与常规同步。
3. 将首批 V2 reader 客户端限制为内部测试账户，再将开关设为 `true`，观察同步、409 冲突和错误率。
4. 如需停止新的迁移，立即将开关改回 `false` 并重建 API 容器。该操作不改写任何密文，也不影响已迁移记录的读取。
5. 如 API 本身异常，回滚到记录的旧镜像 digest；不要通过回写 V1 或修改密文来“回滚”已迁移数据。

## 禁止事项

- 不要在正式服务上以 `latest` 进行首次迁移。
- 不要将主密码、明文配置、密文样本、JWT 或数据库连接串记录到命令历史、日志或发布记录。
- 不要在没有备份和至少两个 V2 reader 客户端验证的情况下启用生产开关。
